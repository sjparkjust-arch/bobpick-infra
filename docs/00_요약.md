# 밥픽(BobPick) 인프라 이관과 부하 테스트

Django 기반 메뉴 추천 서비스의 AWS 인프라를 다른 계정으로 이관하고, JMeter로 한계를 측정해 발견한 결함을 수정한 작업입니다.

| | |
|---|---|
| 기간 | 2026년 9월 14일 ~ 15일 |
| 구성 | ALB + Auto Scaling Group (t3.micro) + RDS MySQL + ElastiCache Redis + CloudFront + WAF |
| 관리 | Terraform (IaC), GitHub Actions (CI/CD) |
| 서비스 | https://bobpick.cloud |
| 상세 기록 | [계정 이관](01_AWS계정이관.md) · [부하 테스트](02_부하테스트.md) |

---

## 1. 계정 이관 — 63개 리소스 재구축

팀 프로젝트로 만든 서비스를 개인 계정으로 옮겨야 했습니다. 서버, DB, 도메인, 배포 자동화까지 전체 스택을 새 계정에 다시 세우고 기존 주소가 그대로 동작하게 만드는 작업입니다.

인프라가 Terraform으로 관리되고 있어 구성 자체는 재현할 수 있었습니다. 문제는 **코드로 재현되지 않는 것들**이었습니다.

| 항목 | 처리 방법 |
|---|---|
| AMI | 계정 간 공유 후 자기 소유로 복사 (스냅샷 권한 동반 필수) |
| SSH 키페어 | 새 계정에서 재발급 후 코드 수정 |
| 도메인 소유권 | Route 53 호스팅 영역 재생성 → 가비아 네임서버 변경 → ACM 재검증 |
| DB 데이터 | 옛 RDS가 이미 삭제되어 시드 명령으로 재생성 |
| S3 버킷명 | 전역 유일 제약으로 신규 명명, backend 설정과 동기화 |

3시간 내에 63개 리소스를 새 계정에 구축했고, 네임서버 변경 13분 뒤 SSL 인증서가 발급되며 서비스가 정상화됐습니다.

**IaC의 가치를 실측으로 확인한 작업이었습니다.** 데이터베이스가 유실된 상황에서도 인프라는 코드로, 데이터는 애플리케이션의 시드 명령으로 복원할 수 있었습니다. 수동 구축 환경이었다면 복구가 불가능했을 상황입니다.

**사전 분석으로 이전 실패를 차단했습니다.** 한 달 전 같은 작업에서 키페어 누락과 Instance Refresh 중복 실행으로 문제를 겪었고, 이번에는 계획 단계에서 미리 처리했습니다. 또한 `terraform plan` 출력에서 의도치 않은 RDS 비밀번호 변경을 발견해 중단했는데, 그대로 진행했다면 애플리케이션이 DB에 접속하지 못하는 상태가 됐을 것입니다.

## 2. 부하 테스트 — 오토스케일링이 동작하지 않았다

JMeter로 부하를 걸기 전 코드를 먼저 점검했고, 두 가지 문제를 발견했습니다.

**오토스케일링 정책이 없었습니다.** ASG는 `min 2 / max 4`로 설정되어 있었지만 `aws_autoscaling_policy` 리소스가 존재하지 않았습니다. CPU가 100%에 도달해도 인스턴스가 늘어날 수 없는 구조였습니다. Target Tracking 정책(목표 CPU 40%)을 추가했습니다.

**WAF Rate Limit이 테스트를 차단합니다.** 5분간 2,000회 제한은 초당 약 6.7회로, 가장 가벼운 테스트(14.79 TPS)에서도 걸리는 값이었습니다. 그대로 두면 서버 성능이 아니라 WAF 응답을 측정하게 되므로, 테스트 IP를 한시적으로 예외 처리하고 종료 후 제거했습니다.

### 정책을 추가했는데도 늘어나지 않았다

부하를 걸자 CPU가 90.55%에 도달하고 응답시간이 기준선 대비 19배로 악화됐습니다. 그런데 인스턴스는 2대 그대로였습니다.

알람 설정을 직접 조회해 원인을 찾았습니다.

```
Threshold: 40.0, EvaluationPeriods: 3, Period: 60초
StateReason: 1 datapoint [90.33] was greater than the threshold (40.0).
```

알람은 **1분짜리 데이터 3개**를 요구하는데, EC2 기본 모니터링은 **5분 간격**으로 수집합니다. 1분 단위 데이터가 존재하지 않으니 조건을 충족할 수 없었습니다. StateReason의 "1 datapoint"가 결정적 근거였습니다.

**정책은 올바르게 설정됐지만 메트릭 수집 주기와 알람 평가 주기가 어긋나 동작하지 않은 것**입니다. 상세 모니터링을 활성화하자 1분 만에 알람이 발동했고, 이후 launch template에 코드로 반영했습니다.

## 3. 증설 구간의 502 에러 40건 → 0건

증설 자체는 성공했지만 전환 구간에서 502 에러 40건(1.91%)이 발생했습니다. JTL 로그를 분석해 원인을 특정했습니다.

```bash
awk -F',' 'NR>1 && $8=="false" {print $4}' scale.jtl | sort | uniq -c
#   40 502
```

`asg.tf`의 user_data 마지막 줄 `systemctl restart gunicorn`이 원인이었습니다.

```
1. AMI 부팅 → gunicorn 자동 시작
2. ALB 헬스체크 통과 → 트래픽 유입 시작     ← 이미 요청을 받음
3. user_data 초기화 스크립트 실행 중
4. systemctl restart → 리스닝 소켓 닫힘     ← 502 발생
```

gunicorn이 AMI 부팅과 동시에 기동되어 헬스체크는 금방 통과하는데, 그 시점에 초기화 스크립트가 아직 실행 중이었던 것입니다.

### 조치

| 항목 | 내용 |
|---|---|
| gunicorn 서비스 파일 | `ExecReload` 추가 — 워커를 순차 교체해 리스닝 소켓 유지 |
| user_data | `restart` → `reload` 전환 |
| user_data | `migrate`·`collectstatic` 제거 — RDS와 S3는 공유 자원이므로 배포 시 1회면 충분 |
| 타겟 그룹 | `slow_start = 60` — 신규 타겟에 트래픽 점진 투입 |
| launch template | 상세 모니터링 활성화 |

`ExecReload`는 AMI 내부 파일이라 인스턴스에서 직접 수정한 뒤 AMI를 재생성했습니다.

### 검증

동일 조건(사용자 100명, 15분)으로 재측정했습니다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 총 요청 | 약 30,000건 | 61,438건 |
| **502 에러** | **40건 (1.91%)** | **0건** |
| 증설 소요 | 약 6분 | 4분 미만 |
| 증설 후 평균 응답 | 600ms | 595ms |
| 증설 후 처리량 | 87 TPS | 87 TPS |

성능은 동일하고 에러만 사라졌습니다. 개선의 내용이 정확히 그것이었습니다.

남은 3건은 502가 아닌 응답 타임아웃(20초 초과)이었으며, 발생 시각이 증설 구간이 아니라 포화 구간과 꼬리 지연이었음을 로그로 확인했습니다.

적용 과정의 Instance Refresh 자체가 첫 검증이었습니다. 인스턴스 2대를 전부 교체하는 10분 동안 초당 1회 요청을 보내며 관찰했고, 502가 단 한 번도 섞이지 않았습니다.

## 4. 한계 측정과 오토스케일링 전 주기

사용자 수를 바꿔가며 5차에 걸쳐 측정했습니다.

| 차수 | 조건 | 처리량 | 평균 응답 | Apdex | 에러율 |
|---|---|---|---|---|---|
| 1차 기준선 | 10명 / 2대 | 14.79 TPS | 93ms | — | 0% |
| 2차 증설 | 100명 / 2→4대 | 87 TPS | 600ms | 0.673 | 1.91% |
| 3차 개선 검증 | 100명 / 2→4대 | 87 TPS | 595ms | 0.673 | 0.00% |
| 4차 한계치 | 300명 / 4대 | 74 TPS | 3,495ms | 0.235 | 0.01% |
| 5차 축소 | 10명 / 4→2대 | 15.51 TPS | 92ms | **0.998** | 0.00% |

**안전 운영 한계는 약 85 TPS, 동시 사용자 100명 수준입니다.**

4차에서 사용자를 3배로 늘렸는데 처리량이 87에서 74 TPS로 **역행**했습니다. 포화를 넘어서면 성능이 악화되기 시작한다는 뜻입니다. 네 페이지의 응답시간이 3.5초로 평준화된 점도 확인했는데, 이는 병목이 애플리케이션 로직이 아니라 gunicorn 워커 앞의 **대기열**임을 의미합니다.

같은 구간에서 인스턴스 하나가 헬스체크 실패로 퇴출됐습니다.

```
11:58:14  taken out of service in response to an ELB system health check failure.
11:58:16  launched in response to an unhealthy instance needing to be replaced.
```

응답시간이 헬스체크 타임아웃 5초를 넘기면서 unhealthy 판정을 받은 것입니다. **단순한 성능 저하가 아니라 과부하가 인스턴스 퇴출을 유발하고, 남은 인스턴스에 부하가 몰려 상황이 악화되는 연쇄 구조**를 실제로 관찰했습니다.

![인스턴스 수와 응답시간](images/lt-24-cw-hosts-latency.png)
*CloudWatch — 파란 선은 정상 인스턴스 수(오른쪽 축), 주황 선은 ALB 측정 평균 응답시간. 증설은 2→4로 한 번에, 축소는 4→3→2로 단계적. 11:58의 계곡이 인스턴스 퇴출 시점*

증설과 축소가 비대칭이라는 점도 실측으로 확인했습니다. 증설은 목표값을 맞추는 데 필요한 용량을 계산해 한 번에 반영하고, 축소는 한 대씩 내립니다. 트래픽이 잠시 줄었다고 성급히 서버를 내리면 재증설 지연으로 장애가 나기 때문입니다.

![CPU 사용률](images/lt-25-cw-cpu.png)
*CloudWatch — 4대로 증설된 뒤에도 CPU가 85~90%를 유지. 목표값 40%에 도달하려면 더 많은 인스턴스가 필요했으나 max_size 4에 막힘*

CPU 그래프는 두 가지를 보여줍니다. 증설 후에도 목표치에 도달하지 못해 **max_size가 실질적 병목**이었다는 점, 그리고 한계치 구간에서 CPU가 오히려 내려간 점입니다. 후자는 부하가 줄어서가 아니라 t3.micro의 CPU 크레딧이 소진되어 스로틀링이 걸린 것으로, 같은 구간의 처리량 역행과 원인이 같습니다.

## 5. 결론

**측정 → 진단 → 개선 → 재측정** 사이클을 완결했습니다. 502 에러 40건을 로그 분석으로 원인까지 특정해 0건으로 만들었고, 오토스케일링이 동작하지 않던 두 가지 원인(정책 부재, 메트릭 주기 불일치)을 근거와 함께 밝혀냈습니다.

JMeter 측정치(클라이언트 관점)와 CloudWatch 지표(서버 관점)가 같은 시점에 같은 방향으로 움직이는 것을 교차 확인해 측정의 신뢰도를 확보했습니다.

### 확인된 개선 과제

**메인 대시보드 추천 로직** — 모든 측정 조건에서 가장 느렸습니다. 협업 필터링 결과를 Redis에 캐싱하면 개선 여지가 큽니다.

**max_size 상향 또는 인스턴스 타입 변경** — t3.micro는 버스터블이라 지속적인 고부하에 부적합하며, 크레딧 소진 시 성능이 급락합니다.

**gunicorn 워커 수 조정** — 워커 3개가 병목이었습니다. t3.micro(2 vCPU) 기준으로는 5개가 적정합니다.

**헬스체크 엔드포인트 분리** — 현재 추천 로직이 도는 `GET /`를 헬스체크에 사용합니다. 부하 시 헬스체크가 먼저 실패하는 원인이며, DB 연결만 확인하는 경량 엔드포인트로 분리하면 연쇄 퇴출을 줄일 수 있습니다.

**배포 파이프라인 중복 제거** — 모든 인스턴스에서 `migrate`와 `collectstatic`이 각각 실행됩니다. 공유 자원이므로 1회면 충분하며, 인스턴스가 늘어날수록 낭비가 커집니다.
